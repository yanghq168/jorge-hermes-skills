# 权权内容平台矩阵

权权名下多个内容账号的每日自动内容生成系统。

## 🤖 Agent 库位置

内容 Agent 的脚本存在两个地方：

| 类型 | 路径 | 说明 |
|------|------|------|
| **执行脚本** | `~/.hermes/cron/scripts/*.py` | 实际运行的 Python Agent 程序 |
| **规范文档** | `~/.hermes/skills/productivity/content-platforms/` | SKILL.md + references/ |

每个 `.py` 脚本就是一个独立的内容 Agent，通过 `cronjob(action='create', script='xxx.py')` 注册定时任务。（v1.5.1）

| 平台 | 脚本 | 定时 | 状态 |
|------|------|------|------|
| 微信公众号「围炉家常话」 | `wechat-article-daily.py` | 每天 07:00 | ▶️ 运行（**MD文件推飞书，不发邮件**） |
| 小红书周末出逃计划 | `xhs-escape-weekend.py` | 每天 10:00 | ▶️ 运行 |
| **全平台内容生成** | **`unified-content-daily.py`** | **每天 17:00** | ▶️ **运行中** |
| 头条号文章 | `toutiao-article-daily.py` | 20:30 | ▶️ 运行 |
| **小红书旅游攻略** | `xhs-travel-daily.py` | **每天23:00** | ▶️ **运行中**（用户长期需要） |

## 🏗️ 通用架构

```
cronjob (定时) 
  → Python脚本 (~/.hermes/cron/scripts/)
    → HTML邮件模板 
      → SMTP发送至 569545015@qq.com
        → deliver=origin 推送到当前对话
```

所有脚本遵循同一模式：
1. 选题库随机抽取（扩充内容）
2. HTML精美邮件模板（渐变色头部、卡片布局）
3. `from config_loader import get_mail_config` 读取邮件配置
4. 纯文本+HTML双版本邮件
5. 输出摘要供确认

- **`references/negative-claim-contradiction-and-identity-collision.md`** — **缺陷二十一「标题承诺了一个否定事实，正文把它推翻了」**（2026-11-18 实测，audit/lint/FP/跨夜碰撞/脚本 **exit 全 0** + 飞书已回查送达，**全程绿灯**仍抓到 5 处读者可见问题）：标题断言「三个子女**一分没出**」，正文后段却写「小儿子转了 5000 块过来」⇒ **读者一回头看标题就发现被耍了**。**根因：现有全部「承诺兑现」类规则都默认承诺是一个「存在」**（某个数字要出现、某句话要出现）——`HOOK_PROMISE` 只认引号词与阿拉伯数字，**否定式承诺（"X 没/未/不 + 动作"）完全在覆盖之外**；`SPLIT_VS_TOTAL`/`SUM_VS_HALF_CLAIM` 查算术冲突，而这是**存在性冲突**。含：① 否定承诺的检测配方（触发词表 + 完成态反查）② **修法三选项**（改后文 / 改标题 / 明写「这 5000 是份子钱不算丧葬费」——保留标题断言同时解释是头条读者最爱的写法）③ **⚠️ 不要做成硬 linter 规则**（语义上「出了丧葬费」≠「出了份子钱」，正则分不出来 ⇒ 必然假阳性 ⇒ 后患是「为了闭嘴改掉对的文案」）⇒ 定位为**通读清单第 ⑯ 条链** + 扫描脚本粗筛 + 人工核对 ④ **人物身份撞车扫描**（A/B 同名 3 处 + 同龄 2 处，当晚**全部假阳性** ——「她的做法跟王阿姨完全不一样」是双故事对比论证法的**标准写法**，判别口径 = 同名是否出现在该故事自己的动作/结局里）⑤ **年龄撞车不是缺陷**（中老年题材 68 岁是主力年龄，撞车是必然的）⑥ **六段式扫描脚本组装方式**（每段独立可失败 + 每段标注「真缺陷」vs「设计约束」）⑦ **🔴「本会话未修改生产源码」必须附三条证据**（三份源文件 mtime / 当日产物数 / history mtime）—— 否则下一轮会话读到报告无法判断该从哪继续

- **`references/cross-field-defect-detection.md`** — **缺陷十三/十四/十五「跨字段·跨夜失配」检测与修复手册**（2026-11-11 实测）：**跨夜同故事碰撞**（`SHADOW_MAP` 只挡当晚，挡不住「前一晚的长文 == 今晚的微头条」—— 实测实例：11-10 长文=随礼人情/老周头烧本子，11-11 微头条=人情往来/同一个老周头；读者连续两封邮件读同一故事；60 天模拟碰撞 **20%**；修法：排除集扩到「当晚+前 N 晚+**后 N 晚**」，长文方向可预测（LRU 无并列时选择唯一，实测预测 30/30 准确）；**守卫夜数调参表**：3/3 碰撞 0/60 且两池覆盖 10/10，**5/5 会把微头条覆盖压到 4/10**）+ **钩子整句在正文里逐字复读**（`HOOK_PROMISE` 只查「有没有兑现」，查不到「兑现方式是整句复制」；检测口径 = 钩子按句切开 → 去标点归一化 → 逐字 `in` 正文，比公共子串更准；**改正文不动钩子**）+ **金句出处标注与实际出处对不上**（模板硬编码「故事A结尾/故事B结尾/文章结尾」，20 条里 9 条不符；**修法是不手改金句而是按实际出处动态算标签** `_golden_labels()`，bigram 重叠率 + 打分用整段故事 + 差距小就标中性「文章金句」——**宁可模糊也不说假话**）。含通用跨字段公共子串扫描脚本 + 「必须调用真实生产函数而不是在测试脚本里复刻逻辑」的踩坑

#### A. 选题池轮换与去重（池子大小 = 轮换周期）

| 纪律 | 说明 |
|---|---|
| **去重窗口必须跟随池子大小** | 固定窗口会让扩库失效。`MAX_RECENT` 与 `TOPICS_POOL` 长度脱钩 ⇒ 同一标题必然按窗口周期复现 |
| **窗口按「条数」算，对微头条是错的** | 长文 1 条/天；微头条 **2 条/天**，同一窗口只覆盖一半天数 ⇒ 改用 **LRU**（取最久未出现的那条） |
| **读写端字段名必须一致** | `_record_topic()` 写 `'key'` / `_pick_topic()` 读 `h.get('direction')` ⇒ `recent` 恒为 `['None',...]` ⇒ 去重**静默失效且无报错**。读取端用 `_hist_key()` 兼容两种字段名 |
| **轮换模拟绝不能读生产 history** | 会污染生产数据并让结论失真（曾据此得出「微头条只覆盖 4/10」的假结论）。用临时文件 + 可注入路径的函数（`_pick_micro_index(used, history_path=None)`），改完 `diff` 确认生产文件未变 |

→ 完整实现与调参：`references/topic-pool-rotation-and-length-engineering.md`、`references/guard-window-vs-rotation-period.md`

#### B. 守卫窗口 vs 轮换周期（跨夜碰撞的第二个根因）

**守卫窗口必须 ≥ 被测池的轮换周期**（`SHADOW_GUARD_NIGHTS` vs 池大小 ÷ 每晚条数）。
回看窗口同理：碰撞回看必须取 `max(轮换周期, 守卫夜数)`，手写 `range(1,4)` 只看 3 夜 ⇒ **漏报**，
「碰撞 0/60」是假绿。排除集要含**前 N 晚 + 后 N 晚**（只挡往前看会漏「微头条先出、长文后出」）。
落地必须**「换孪生故事 + 动态守卫」配套做**：单做一件都不够（加守卫会把方向覆盖压到 4/10）。

→ `references/guard-window-vs-rotation-period.md`、`references/cross-field-defect-detection.md`

#### C. 审计工具自身的失败模式（退出码语义）

**退出码有三种含义，方向完全相反：**

| 退出码 | 含义 | 该动谁 |
|---|---|---|
| `0` | 干净 | —— |
| `1` + 规则名 + 命中项 | 内容有问题 | 改文案 |
| `1` + stderr 有 traceback（`SyntaxError`/`NameError`） | **工具自己坏了** | 修工具，**别改文案** |
| `2` | **工具/参数用错**（自检失败、装配不出正文、`--pool` 指错文件） | 修工具或改参数 |

**判别口诀：先看 stderr 有没有 traceback，再决定动谁。** 照惯例「exit 1 ⇒ 改文案」会把本来正确的文案改坏。

- **跑审计工具必须单独看退出码**，别用管道吞掉它：`... > /tmp/lo.txt 2>/tmp/le.txt; echo "REAL EXIT=$?"`。
  `| tail -30; echo $?` 打印的是 **tail 的退出码** —— 曾因此连续两晚把「linter 自检崩溃」误读成「全绿」。
- **stdout 空 + stderr 有 traceback = 工具崩了**，不是内容有问题。
- **自检崩溃应当 `raise SystemExit(2)`**，否则「工具坏了」被误读成「内容有问题」。
- **「写了函数」≠「规则生效」**：必须造真实反例实测**会 fire**（断言 exit 1 + 报出规则名）。
  只跑干净内容 exit 0 证明不了规则接上了（空集合也 exit 0）。
- **新落地的校验器必须真跑一次**（连续两晚踩过「首次调用即腐烂」）。
- **🔴 `exit 2` 还有第四种来源：argparse 拒绝了不存在的参数（2026-11-25 实测）。**
  stderr 形如 `error: unrecognized arguments: --extensions /path/x.py` 或
  `error: the following arguments are required: --pool` —— **这是「你把命令敲错了」，
  不是「工具装配不出正文」**，两者都返回 2 但方向完全不同：前者改命令行，后者修工具。
  - **判别口诀**：stderr 里出现 `unrecognized arguments` / `the following arguments are required`
    ⇒ **纯命令行问题**，重新看一眼该脚本的 `--help` 再跑一次即可；
    stderr 里出现 `装配不出正文` / 自检失败信息 ⇒ 才是工具侧问题。
  - **每个脚本的参数集不同，必须先看 `--help`**。2026-11-25 实测：`verify_cross_night_collisions.py`
    **不接受 `--extensions`**（给了就 exit 2），而 `check_pool_type_false_positives.py` /
    `scan_pool_defects.py` / `lint_content_consistency.py` **接受**。
    把「给所有检查器都加 `--extensions`」当成肌肉记忆 ⇒ 在不接受它的脚本上直接 exit 2。
  - **防御动作**：跑任何检查器前先 `--help` 一次（1 秒成本），
    或把**每个脚本各自的完整命令行**记进下面的参数契约表并复制粘贴，不要凭印象拼 flag。
- **不要留第二份旧 linter 在生产目录** —— 两个实现会漂移，迟早跑错那个。删掉，或让它 import 新版。
- **审计产物要测「装配后的最终产物」，不是中间返回值**：`generate_article()` 只返回长文 HTML，
  微头条 HTML 在 `send_email()` 里才拼上；**微头条字数要测 `content` 字段**（受 150–250 约束的那个），
  不是渲染块。用 `scripts/audit_rendered_article.py`，别手写正则。

→ `references/audit-tool-death-and-prompt-language.md`、`references/pool-wide-scan-and-linter-syntax-death.md`

#### D. 新增检查器的「三步验证」（前两步都不够）

给 linter 加规则时必须走完三步：

1. **正例不报**（exit 0）
2. **反例必报**（造真实反例，断言 exit 1 且报出规则名）
3. **跨池型不误报**（第三步最容易漏）—— 对**每一个**选题池各跑一遍，把命中项连同该池正文字段打出来**逐条人工核对**，
   不要只看汇总数（汇总 15 处时实际只有 1 处真缺陷）

**根因**：装配函数只认 `story_*` 字段，而微头条池正文在 `content` + `micro_dialogue` ⇒ 微头条正文被装配成空串 ⇒ **整池假阳性**。
修法：`if g('content'): return content + micro_dialogue`（微头条）否则走 `story_*`（长文）。
**新增装配函数前先看有没有现成的池型分叉助手（如 `_units_for()`），优先复用** —— 自造第二套装配逻辑 = 迟早与主流程漂移。

→ `references/hook-promise-and-title-payoff-audit.md`、`references/scanner-false-green-and-quote-vs-prose-echo.md`

#### E. 参数集不全会制造假阳性（比漏报更危险）

**任何接受 `--extensions` 的检查器（`check_pool_type_false_positives` / `lint_content_consistency` / `scan_pool_defects`）漏传它 = 制造假阳性。**
假阳性长得和真缺陷一模一样，会诱导你把**本来正确**的文案改软。

**动手改文案前必须先做「兑现点定位」**：用 `grep` 在**全部源文件**（生成器 / 扩写池 / 扩写段落）里搜那句话到底在不在。
**兑现点存在于你漏掉的那个文件里 = 装配口径问题，不是内容缺陷。**
**防御动作**：把「三个源文件 + 全部参数」当一条命令**复制粘贴**，不要每次手敲。

#### F. 「全绿 ≠ 内容对」—— 逐段通读 + 手动加数

自动化只能覆盖**已编码的缺陷族**。新族必须人工通读 + 事后沉淀。**通读清单已扩到 24 条链**，
其中 **⑱–㉒（人数链 / 数量自洽链 / 标题事实名词链 / 量词三处链 / 字数断言链）= 全是读者能用手指点着数出来的断言 ⇒ 优先核这一类**。

**通读的通用问法（逐段提问式核验，不是「读起来顺不顺」）：**

| # | 问法 |
|---|---|
| 1 | 标题的人数，正文有几个人在做这件事？ |
| 2 | 标题的事实性名词（再婚/婚前/过户），正文交代了吗？ |
| 3 | 人物对资产的描述 = 当前事实吗？ |
| 4 | 相对时间与绝对时间指同一件事吗？ |
| 5 | 规则与后续执行矛盾吗？（「等我俩都走了」但她先走了） |
| 6 | 当时这个人活着还是死了？ |

**六条基础链**（任何题材通读都盯）：① 年龄链 ② 金额链 ③ 时长链 ④ 同属性取值链（**按「同一人物」分组比，不是整篇比**）⑤ 币种口径链 ⑥ 汇总链。

**「读者能数出来的断言」一律改写成不可数的定性表述**（「只说了一句话」→「只交代了一句」；「两个孩子」→「一家人」）。
**不要去数字并改数字** —— 改了会连带正文里引用该数字的其他段落。

→ 全部缺陷族实录：`references/` 下 `*-audit.md` / `*-chains.md` 文件（见上方「参考资料」目录）

#### G. 承诺兑现的四种口径（`HOOK_PROMISE` 的盲区）

`HOOK_PROMISE` 只认**引号词 + 阿拉伯数字**。以下四类承诺**完全在覆盖之外**：

| 口径 | 例子 | 处置 |
|---|---|---|
| ① **引语/数字** | 钩子说「38度5」，正文没写 | 硬规则 `HOOK_PROMISE`（已落地，实测会 fire） |
| ② **量词级** | 「三个儿女」「一句话」「只说了四个字」 | 通读清单 + 扫描脚本粗筛。**改写成不可数表述** |
| ③ **否定式承诺** | 标题「一分没出」，正文写「转了5000」 | ⚠️ **不要做成硬 linter 规则**（「出了丧葬费」≠「出了份子钱」，正则分不出来 ⇒ 必然假阳性 ⇒ 后患是「为了让规则闭嘴去改对的文案」）。走通读清单第 ⑯ 条链 + 扫描脚本 + 人工核对 |
| ④ **场景型** | 钩子「住院那三个月」vs 正文「在家摔了一跤躺了三个月」 | 通读清单第 ⑳ 条链 + 人工核对 |

**同一承诺在五处各说各的**（`title` / `hook` / `story_a` / `viewpoint` / 互动问题）⇒ 通读清单第 ⑲ 条链。
**否定承诺按「动作」归一化再比对**（「没人请他」≈「没人来」≈「一个都没来」在情感语境里是同一件事）。
**以标题为唯一真源，五处一起收敛成一个措辞。**

**「改正文，不动钩子」是纪律，但有例外**：钩子与正文**核心情节**不是同一场景时、或钩子与结局绝对化表述自相矛盾时，**必须改钩子**。
**观点句优先写成二选一问句**（「是子女不孝顺，还是老人自己想换种活法？」）—— 一次性化解断言互斥，且更适合头条评论区互动。

#### H. 复读的判定纪律（引语级 vs 散文级）

- **引语级重叠 = 设计约束**（`HOOK_PROMISE` 强制钩子引语必须出现在正文），**散文级重叠 = 真缺陷**。
  引语级复读的修法 = **保留钩子原句 + 在正文兑现点补新细节**（动作/心理/后果），不是删、不是换说法。
- **全字段两两公共子串扫描阈值用 8 字，不是 linter 的 10**（当晚 3 处真实复读里有一处恰好 9 字，差一个字漏报）。
  范围必须含扩写段 `ext_a`/`ext_b`，也要含 `story_b_ending`↔`viewpoint` 这类**两个正文字段之间**的复读。
- **代词人称变体导致的准复读**：`你/我/您/咱` 常可互换，逐字比对看不见它们是同一句话 ⇒ 归一化单字代词后再算公共子串（永久规则 `GOLDEN_ECHO_PRONOUN`）。
- **钩子整句在正文逐字复读**：钩子按句切开 → 去标点归一化 → 逐字 `in` 正文（比公共子串更准）。**改正文不动钩子。**
- **涉及「钩子 ↔ 正文」的断言要数出现次数，不能用 `not in`** —— 纪律是「改正文不动钩子」，钩子本来就该保留那句话。
  正确写法：`full.count(钩子短语) == 1`。
- **金句复读**（永久规则 `GOLDEN_ECHO`，阈值 ≥10 字）：判定范围**必须含 `story_a_ending`/`story_b_ending`**；微头条池没有 `golden1/2/3` ⇒ 直接返回 `[]`（否则整池假阳性）。
  **修法是改金句不是改正文**；重新指派 golden 时**要连 viewpoint/action 一起改**，否则复读只是从一处搬到另一处。

#### I. 金句标签的出处判定（`_golden_labels()`）

- **金句是结论卡不是金句卡** ⇒ 必须与当篇故事事实同向。方向冲突时**加限定词收窄适用范围**，不要推翻重写。
- **region 划分必须细到子段落级**（A正文/A对话/A结尾/B正文/B结尾/观点/行动 共 7 段）。**拆分原则：每个 region 必须语义上可独立被引用。**
- **拆细与中性阈值是两条正交修复，不能互相替代**。判中性用 **best − second 的差距**而不是 best 绝对分数，且 `second` 必须含**同故事的其他子段**。
- **中性阈值 0.05 → 0.10** —— 宁可标「文章金句」，**不说假话**。
- **打分管线必须按「池型分叉」**（微头条池无 golden ⇒ 直接返回中性标签）。

#### J. 改生产源码的三个陷阱（`py_compile` 通过 ≠ 改动生效）

1. **`str.replace(old, new, 1)` 可能命中 docstring 而不是代码**（文件头升级说明里常出现与代码一样的字符串）⇒ **锚点必须带上下文**（前后各一行），改完**回读断言运行值**。
2. **按花括号深度切分 list 字面量再 join 会留下孤立逗号** ⇒ `SyntaxError`。批量改 list/dict 字面体时**重新生成整个字面量**，不要切片段再拼接。
3. **锚点照抄记忆必失败**（转义形式、差一个字）⇒ 匹配失败先 `src.find(prefix)` 打印真实上下文，**别猜原文**。

**通用规则：改完源码必须做一次「运行时行为断言」，不能只看 `py_compile` + 「replace 成功」。**
最省事形态 = 改完 import 一次打印关键常量，确认等于期望的新值。

- **锚点必须用「最小唯一片段」**；`assert count==1` 后**逐条立即落盘**（批量替换里只要有一条匹配失败，
  「全部成功才落盘」的实现会把已成功的编辑一起丢弃）。匹配失败先打印真实源文本再改。
- **改完必须回读断言**：`assert old not in back and new in back`（**允许新串包含旧串作为前缀**，不要写 `assert new not in back`）。
- **改任何数字前先列「整条链」**：找出**被算式引用、不能动**的那一处，改**不参与算式**的那几处。
  一条数字被三个以上位置引用时，改它之前必须先画依赖图。
- **改文案会把字数约束顶出去** ⇒ 改完**立刻量 CJK 字数**（微头条硬约束 150–250），别等渲染才发现。
  ⚠️ 微头条字数按 **CJK 字符数**算，不是 `len()`。
- **任何要进生产池的条目必须先过两道闸**：① CJK 字数在硬约束区间内 ② 与长文池所有故事人工比对过（同人物/同事件/同金句/同金额）。
  **过不了就不进池**。「已定位根因 + 已给出方案」可以写进报告，**「已改好」不行**。

#### K. 隔离 harness（不重跑生产也能证明修复生效）

**Case R（改源码不重跑）的「验证」这一步**：直接跑生产脚本 = 违反 Case R；不验证 = 不知道修复有没有落地。

五步：① `importlib.util.spec_from_file_location` 加载生产脚本（文件名带连字符不能 import）
② 把 `HISTORY_FILE`/`MICRO_HISTORY_FILE` 指向**临时目录** ③ monkey-patch 强制选中要验的方向
④ 调**真实生产函数**并**自己拼微头条**（`generate_article()` 只返回长文；`generate_micro_articles()` 签名会变，先 `inspect.getsource()`）
⑤ 对隔离产物跑审计 + 跑**双向修复点断言**（旧串 `not in` + 新串 `in`，只查新串会漏「改错段落」）。

跑完核验**生产状态零污染**（产物数不变 + history mtime 不变 + 无残留临时文件）。
⚠️ **禁止用 harness 产物去补发** —— 那等于投递第二份内容。报告里必须写明「读者手上的那份仍是修复前版本，修复从明晚首跑生效」。

**断言要「钉语义要点」，不要「钉计划中的逐字措辞」** —— 落地措辞常与计划不同，**断言失败 ≠ 修复失败**。
先确认产品是不是真的还错，再决定改文案还是改断言。一条断言 = 一个位置。

→ `references/isolated-verification-harness.md`、`references/field-echo-and-sum-vs-total-audit.md`

#### L. 证明「改动带来了行为变化」要跑反向对照

**只跑「现在碰撞 0/60」证明不了任何事**（无法区分「改好了」与「检测器坏了 / 本来就没碰撞」）。
正确做法：同一份种子 history、同一段模拟、同一份检测口径，**只换池/映射/守卫参数**，跑出「修复前」与「修复后」两组数据对比。
⚠️ 「修复前」配置**必须从备份脚本 import 真实旧池** —— 手搓 stub（只填 direction/title）会在渲染时 `KeyError: 'tags'`。
⚠️ 每组模拟开头要 `shutil.copy` 重置种子，否则第二轮跑的是第一轮的后状态、不可比。

→ `references/pool-wide-scan-and-linter-syntax-death.md`

#### M. 诊断探针可能自己把整条管线跑一遍（比改源码更危险）

**判别口诀：探针有没有调用生产脚本的入口函数？有 ⇒ 就是在跑整条管线；守卫帮不上忙**（守卫判断 `__name__`，你主动调用入口函数时它不保护你）——
本例脚本**本来就有守卫**，仍然踩坑（多生成并多投递了一份文章，history 多 3 条 ⇒ 次日 LRU 轮换被带偏）。

**危险来自「import/调用入口函数」，不是来自路径** —— 探针放在 `/tmp` 并**不**安全；`exec(open(...).read())`、`runpy`、`importlib` 手动调用入口都等价。

预防：① 多数「我想知道生产脚本怎么写的」**根本不需要执行它** —— 只读源码文本就够
② 真要调真实生产函数 ⇒ 走隔离 harness ③ **零生产副作用预检**：探针跑前跑后各执行一次「当日 outbox 产物数 + history mtime」。

**回滚顺序（history 最容易被忘，却最影响次日轮换）**：删飞书附件**并 API 回查 `deleted=True`** → 删重复 outbox HTML
→ 修正 `PENDING_*.html` 软链接指向唯一正确稿 → **回滚两个 history 文件**（先备份 `*.bak_<YYYYMMDD>_<HHMM>`）
→ 报告附「三份源文件 mtime + 当日产物数=1 + history 条目数」证据链。

**「本会话未修改生产源码」也必须附三条证据**（三份源文件 mtime / 当日产物数 / history mtime）——
否则下一轮会话读到报告无法判断该从哪继续。

→ `references/probe-script-triggering-production-pipeline.md`

#### N. 扫描器「假绿」三重漏报

① 段⑥ 只认**同一动词**（标题「一分没出」vs 正文「转了5000」⇒ 不 fire）
② 段① 按句号切分把「她说：」前缀粘进引语 ⇒ **引语级复读全漏报**
③ **微头条池根本没被扫**（只装配 `TOPICS_POOL`）

**「扫描器报无命中」必须先做反向验证** —— 造一个已知有缺陷的反例（用修复前的备份当反例），断言它**会**被报出来。
沿用「只跑干净内容 exit 0 证明不了规则接上了」，现推广到**所有粗筛脚本**。
现成工具：`scripts/verify_scanner_fires.py <negative-promise|blindspot> --scanner <扫描器.py>`。

**粗筛脚本不是判定器**：命中 ≠ 缺陷。**假阳性必须逐条人工确认，不能看到告警就改文案** ——
会把对的改回错的。当晚「她的做法跟王阿姨完全不一样」是双故事论证法的**标准写法**，不是缺陷。

**🔴 实测命中/真缺陷比例（2026-11-25）：粗筛报 8 处，真缺陷 0 处。**
分诊三步法（先看段号定性质 → 看兑现点是否带新细节 → 否定承诺找解释句）见
`references/negative-claim-contradiction-and-identity-collision.md` §三。
**其中「否定式承诺」类命中是最容易误改的一类** —— 正文若已明写「这5000是份子钱不算丧葬费」
这类解释句，扫描器仍会报（它不认识解释句）⇒ **该修法一旦落地，命中会永久存在**，
每晚靠人工分诊排除即可，**不要因为它每晚都报就去改文案**（改掉解释句反而是倒退）。

→ `references/scanner-false-green-and-quote-vs-prose-echo.md`

#### O. 全池回扫优于逐晚修（一次修 9 个方向）

把「当晚复读扫描」升级成「**全池 20 条**」：一次跑出 21 处、分布 9 个方向。
**每个方向单独看只有 1 处（不到「值得单独修」的阈值），合起来才是真实规模。**
只看当晚 ⇒ 每晚只修 1 处，要修 10 个晚上；一次全池 ⇒ 一个晚上修 11 处。

修完立刻再跑一次全池扫描确认命中数下降；剩余命中**逐条人工核对** ——
一部分是**设计约束不是缺陷**（钩子必须兑现自己的引语 ⇒ hook↔正文出现同一句有时是必须的），这类**不要改**。

**锚点不确定时先跨三个源文件定位**（生成器 / 扩写池 / 扩写段落）：
`for f in 三个文件: print(f, txt.count(key))` 先定位再改 —— 当晚连踩 3 次「以为在这个文件、实际在那个文件」。

→ `references/pool-wide-scan-and-linter-syntax-death.md`、`references/field-echo-and-sum-vs-total-audit.md`

#### P. 其它硬规则（散点，但每条都踩过坑）

- **脚本文件名带连字符 ⇒ 无法 `import`** ⇒ 用 `importlib.util.spec_from_file_location`。
  不要依赖 `sys.path[0]`（cron 下是脚本目录、测试下是 cwd），扩库模块要显式插入 `__file__` 所在目录；
  扩库失败要有 `except ImportError` 兜底 + 告警，不能让整条管线挂掉。
- **脚本自带的检查清单数字必须被自动断言** —— 清单写着「1500字以上」但实测每篇只有 813–1159 字，**没有一篇达标**。清单是愿望，从来没人量过。
- **检查清单会漂移，而且它被渲染进产物发给读者** —— 改发件人时漏改清单行，
  导致**每篇文章都在对读者说错的发件人名**。**规则：任何在多处出现的值（品牌名/发件人/版本号/路径）都要对着唯一真源 grep 断言**；
  被渲染进产物的字符串漂移了＝出错了信息给用户。
- **配图提示词必须纯英文** —— 中文片段会被模型当成「要画在画面里的文字」⇒ 渲染出乱码汉字。
  查 `cover_prompt` + `in_image_prompts[*].prompt`；**不要**查 `*.desc`/`*.scene`（那两个是中文给人看的，中文是正确的）。
  `in_image_prompts` 是**列表**，不能靠顶层遍历，要单独走一条。
- **周期频次 vs 年度汇总**（「每两周来一次」= 26 次，但汇总写「来了24次」）—— 读者一按计算器就穿帮。
- **f-string 内禁反斜杠**（Python 3.12）—— 先拼中间变量再塞进 f-string。
- **持久化日志要早做，别留到最后做清理** —— 工具调用额度随时可能截断。**审计/修复是可选项，持久化不是。**
- **互动问题必须与「标题的承诺」同措辞**，并按方向专属池绑定（`DIRECTION_QUESTIONS`）——
  用与内容无关的通用随机池 ⇒ 读者刚看完被儿媳赶走，结尾被问「轮流养老这事你支持吗」，评论区必然答非所问。
  **新增方向时必须同时补上它的问题**，否则静默回落到通用池。验证用「跨方向污染检测」：每方向连抽 40 次，断言集合 ⊆ 该方向自己的池。

### 用户质量反馈（2026-05-28）

**问题1：邮件连发被QQ邮箱拦截**
- 问题：同时发多封邮件（公众号+头条+小红书），QQ邮箱当天触发异常
- 解决：先发1封测试→用户确认OK→再发全量。不要连发3封以上

**问题2：标题有双层书名号**
- 问题：`《《竖版粉彩...》》` → `make_title()` 返回值包含《》再被外层再加一对
- 解决：标题模板直接写 `《xxx》`，不要再套

**问题3：钩子太通用，没有场景感**
- 问题：开头说"刷到这个话题"太刻意，像机器人写的
- 解决：钩子必须有具体场景+人物+动作，例如：
  - ❌ 差："刷到这个话题，我翻了很多文章"
  - ✅ 优："前天深夜，我收到一条读者留言，半天没缓过来"
  - ✅ 优："上周回老家，看到邻居王大爷坐在门口发呆，眼眶红红的"

**问题4：内容与话题词不匹配**
- 问题："竖版粉彩盛典"是审美话题，但science模板套用了通用科普逻辑
- 解决：话题分类要更细——审美/时尚/生活类 → life模板；科普/知识类 → science模板

**问题5：缺少真实故事细节**
- 问题：故事没有具体的人名、地点、数字、对话，读起来像编的
- 解决：每个故事必须有"3元素"：名字（王大爷/老李/小强）+ 具体场景（老家/公司/医院）+ 对话（"我没想到..."/"你凭什么..."）
  - ❌ 差："有人跟我说，他很迷茫"
  - ✅ 优："老李跟我说：'我在公司干了八年，年年第一，现在说我不会带团队？'"

**问题6：标题没有冲突感**
- 问题：标题平铺直叙，没有张力，点击率低
- 解决：爆款标题公式 = 冲突/对比 + 具体数字 + 情绪词
  - ❌ 差："跟着出版社编辑沉浸式改稿：看完终于明白了"
  - ✅ 优："跟着出版社编辑改稿：我发现99%的人连初稿都不会写"
  - ✅ 优："竖版粉彩盛典刷屏，但看懂的人不到1%"

**问题7：缺少配图**
- 问题：公众号文章没有实际配图，只有生图提示词
- 解决：HTML模板中需要加入实际的图位说明（封面图放哪里、正文图放哪里、结尾图放哪里），不能只给提示词

def format_hot(value):
