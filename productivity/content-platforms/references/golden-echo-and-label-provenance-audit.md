# 缺陷九：「金句复读」与「金句标签对不上实际出处」（2026-11-08 头条号实测）

> 这是 `references/hook-promise-and-title-payoff-audit.md`（缺陷八）之后的**第九类内容质量失败模式**，
> 也是**第三类「跨字段失配」**。前两类是钩子↔正文对不上、数值↔数值对不上；
> 这一类是**同一句金句在两个字段之间重复**，以及**金句的「标签」与它的「实际出处」对不上**。

## 一、现象：同一段话在同一篇里连说两遍

2026-11-08 头条号那篇《68岁老两口，儿子在美国一年回来一次…》的审计结果**全绿**：

```
audit_rendered_article.py  → ✅ 全部检查通过（正文 3412 中文字，结构 10/10，配图 7 块，标签 13 个）
lint_content_consistency.py → ✅ 解析器自检通过 + ✅ 20 条选题（10 条扩写）未发现数值链/角色/频次矛盾
脚本 exit 0 → HTML 渲染成功 → 飞书附件送达并回查确认（msg_type=file, deleted=False）
```

但手工写检测器扫描后命中 **27 处**（阈值 ≥10 字公共子串），修完剩 **0 处**。

### 为什么这是读者看得见的

头条长文的结构是「正文里埋一句金句」+「结尾『💡 3个金句（截图转发用）』区把金句再列一次」。
读者从正文读到那句金句 → 滚到底 → 在金句卡里**又看到同一句**。
长文读者对重复极其敏感 —— 这不是「内容正确但表述啰嗦」，是**明显的编辑事故**。

### 为什么现有检查器 100% 逃过

- `audit_rendered_article.py` 测**长度与结构**（字数、段落齐不齐、配图够不够、标签几个）。
- `lint_content_consistency.py` 测**单字段内的算式**与**角色是否凭空多出**。

**两者都不测「字段 A 里的这句话是不是也在字段 B 里出现过」。**
这与缺陷五（数值算不通）、缺陷六（孤儿扩写）、缺陷八（钩子不兑现）是**同一种盲区**：
**单字段自洽，跨字段失配查不到。**

## 二、🔴 附带发现：更根本的「金句标签与实际出处对不上」

模板里写死了三个标签：

```python
【金句1】故事A结尾   → {golden1}
【金句2】故事B结尾   → {golden2}
【金句3】文章结尾   → {golden3}
```

**但 `golden1/2/3` 是按「池槽位」写的，不是按「它实际出自哪一段」写的。**

2026-11-08 实测：14 条长文里，`golden1` 出现在其标注的「故事A结尾」的只有 **0 条**；
`golden2` 出现在「故事B结尾」的 **0 条**；`golden3` 出现在 viewpoint/action 的 **1 条**。

最刺眼的实例（就是当晚发出去了那一篇）：

> 远居赡养 golden1 = 「钱是流水，房子是根。钱花完就没了，房租五年是确定的。」
> —— 这句实际出自**故事B**（钱大爷的台词），却被标成 **【金句1】故事A结尾**。

读者看到「【金句1】故事A结尾」下面跟着一句根本不在故事A里的台词，
会以为文章排版错乱 —— 而故事A讲的是老两口的儿子，老王救场；故事B讲钱大爷自己租房。

**修法二选一**：
- **A（推荐）**：把 `golden1/2/3` 重新指派到它们**真正出自**的那一段（本次对 4 条长文做了重指派）；
- **B**：改标签文字，放弃「故事A结尾 / 故事B结尾」这种具体出处声明，改成「金句1 / 金句2 / 金句3」。

⚠️ 无论选哪个，**标签是会被渲染给读者看的**（`CHECKLIST_ITEMS` 同理），
不是注释 —— 标签与内容不一致 = 把错误信息发给用户。

## 三、检测口径：最长公共连续中文子串

不要试图用语义理解判断「这句金句是不是被复读了」—— 不可靠、不可复现。
**用字符串精确断言**：金句与正文任一字段存在 **≥10 字的连续公共中文子串**即报。

```python
def cjk(s):
    return ''.join(re.findall(r'[一-鿿]', s or ''))

def longest_common(a, b, minlen):
    """a、b 的最长公共连续子串（>= minlen），没有则返回 ''。"""
    best = ''
    for i in range(len(a) - minlen + 1):
        sub = a[i:i + minlen]
        if sub not in b:
            continue
        k = minlen
        while i + k < len(a) and a[i:i + k + 1] in b:
            k += 1
        if k > len(best):
            best = a[i:i + k]
    return best
```

### 阈值取 10 的理由

- < 10 字：多为常见词组（「不是孝顺」「让你饿不死」），假阳性多。
- 10–14 字：仍有少量自然重叠（如「老人对抗孤独的三把钥匙」本就是金句的改写版）——
  这类要**人工逐条核对**，不要只看汇总数。
- 实测 27 处命中里，**全部是人工核对后确认为真缺陷**，但需要人看过才敢批量改。

### 装配口径：必须覆盖**全部**正文字段

判定范围必须包含：

```
story_a / story_a_dialogue / story_a_ending
story_b / story_b_ending
viewpoint / action
+ 对应方向的扩写段落（ext_a / ext_b）
```

⚠️ **只扫 `viewpoint` + `action` 会漏掉一半** —— 本例最初只扫这两个字段，
扩到 `story_a_ending` / `story_b_ending` 后才抓出养老院 / 远居赡养 / 房产纠纷那几处
（`golden3` 出自故事B结尾，是被 `story_b_ending` 复读的）。

## 四、给 linter 新增 `GOLDEN_ECHO` 规则的契约

> ✅ **2026-11-08 已落地并实测会 fire**（见下方「落地结果」一节）。

### 函数签名

```python
def check_golden_echo(topic, ext):
    """金句 golden1/2/3 被正文任一字段整句复读即报。

    返回 [(code, msg, ctx), ...]；干净返回 []。
    """
```

- `topic` 传**整条选题 dict**（不是文本）—— 需要同时读 `golden1/2/3` 和各正文字段。
- `ext` 传该方向的扩写（`None` 或 tuple）。
- 内部按**池型分叉**：微头条池没有 `golden1/2/3` → **直接返回 []**（否则整池假阳性）。

### 必须接进 `lint()` 主流程

⚠️ **「写了函数」≠「规则生效」** —— 这是本项目连续踩的第三个坑
（`ORPHAN_CHARACTER` 空转两晚、`HOOK_PROMISE` 空转一天）。
新规则**必须**在 `lint()` 里有明确调用路径，并**用真实反例实测会 fire**。

### `_self_test()` 必须配三条算例

```python
# ① 正例不报：金句与正文各说各的
ok = check_golden_echo({'golden1': '钱是流水，房子是根。钱花完就没了。',
                        'golden2': '孝顺分两种：给钱的孝顺让你饿不死。',
                        'golden3': '我不把后半辈子押在一个不能到场的人身上。',
                        'viewpoint': '子女不在身边，不是孩子的错。',
                        'action': '算清楚每月缺口，别全靠汇款。'}, None)
assert not ok

# ② 反例必报：golden2 被 viewpoint 复读
bad = check_golden_echo({... 'viewpoint': '孝顺分两种：给钱的孝顺让你饿不死，到场的孝顺让你不孤单。' ...}, None)
assert bad

# ③ 跨池型不误报：微头条池（无 golden 字段）不得报
assert not check_golden_echo({'title': '微头条标题', 'content': '这是一条微头条正文。',
                              'micro_dialogue': '弟弟说：我不是不帮。'}, None)
```

### 退出码语义不变

`0` = 内容干净 / `1` = 内容有问题 / **`2` = 工具自己坏了**（自检失败）。

### 落地结果（2026-11-08）

- 规则已接入 `lint()` 主流程（`lint()` 内第 ⑥ 步，产出 `field='金句复读'`）。
- `GOLDEN_ECHO_MINLEN = 10` 常量定义在 `NUM_IGNORE` 之后。
- `_self_test()` 三条算例全绿（自检输出仍是「✅ 解析器自检通过」）。
- ✅ **实测会 fire**：造临时 pool（golden2 被 viewpoint 复读）→ **exit 1** 且报出 `GOLDEN_ECHO`。
- ✅ **跨池型不误报**：微头条池（无 `golden1/2/3`）返回 `[]`。
- ✅ 修完 12 处文案后，全库 `exit 0`（20 条选题 + 10 条扩写干净）。

## 五、修法：改**金句**，不要改**复读它的那一段**

读者看到的顺序是「正文 → 金句卡」。**金句卡是提炼物，正文是叙事主体。**
所以要改的是**金句的措辞**，让它跟正文那段的表述**不同角度、不同句式**，而不是反过来
把正文改得像金句（那样会毁掉正文节奏）。

### 实战示例（远居赡养）

原状：`golden1` = 「钱是流水，房子是根。钱花完就没了，房租五年是确定的。」
—— 与 `story_b_ending`（钱大爷的台词）整句重复。

修法：把 `golden1` 改成**故事A**（老两口 + 老王）自己的收束，
把 `golden2` 改成**故事B** 的收束，再把 `golden3` 留给文章级观点：

```python
"golden1": "孩子给的是钱，隔壁老王给的是人。钱能请护工，请不来一个守在床边的人。",
"golden2": "房子是别人给的，退路是自己留的。手里有退路，腰杆才硬。",
"golden3": "孝顺分两种：给钱的孝顺让你饿不死，到场的孝顺让你不孤单。",
```

⚠️ **重新指派 golden1/2/3 时要一起改 viewpoint/action**，
否则「A 挪到 B」只是把复读从一处搬到另一处 —— 本次远居赡养就遇到过
（golden2 从 viewpoint 挪进 golden2 后，仍与 `story_b_ending` 重复 → 再改一次）。

同一晚还抓到 **1 处「同角色称呼链」硬伤**（11-07 会话修了兄弟姐妹方向，**漏了赡养义务**）：

## 七、给发布前检查清单新增两条（会渲染给读者）

`CHECKLIST_ITEMS` 不是注释，它被拼进文章底部的「发布前检查清单」区块发给读者：

```
"3个金句有没有在正文里被复读？（同一段话出现两次 = 编辑事故）"
"金句的标签（故事A/故事B/文章结尾）跟它实际出自的那一段对得上吗？"
```

## 八、通用教训（可迁移到任何「摘要卡 + 正文」型内容产品）

1. **「摘要/金句卡」是第二个出场点，不是第一个。**
   任何把同一段文字渲染两次的结构（正文 + 摘要卡 / 开头 + 结尾 / 邮件 + 附件）
   都会天然产生「复读」缺陷。**规则要按「跨字段重复」来查，不是按「字段内自洽」来查。**
2. **标签是产品的一部分。** 凡是会被渲染出去的字符串（标签、清单项、版本号、
   发件人名），都要对着真源断言 —— 标签写「故事A结尾」而内容出自故事B，
   读者会当成排版错乱。
3. **人工通读要逐方向、逐扩写段落过。** 12 处复读分布在 8 个方向，
   一次性「通读主干」会漏；扩写段落必须单独读一遍。
