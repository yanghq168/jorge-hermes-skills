# 内容自洽性缺陷（缺陷五）：数字算不通、角色凭空多出

> 2026-11-01 头条号审计实测发现。这是继「池子 / LRU / `str.format()` / 清单漂移」
> 之后的**第五类内容质量失败模式**，也是最隐蔽的一类。

## 为什么它比其他四类更危险

前四类（池子大小、去重窗口、`str.format()` 丢弃 kwargs、清单漂移）都能被现有
工具抓到：`audit_rendered_article.py` 会报字数不够、结构缺段、配图不足。

**自洽性缺陷全部是静默的**：

```
脚本 exit 0 → HTML 渲染成功 → 飞书附件送达 → audit_rendered_article.py 报
「✅ 全部检查通过」 → 用户收到一篇「看起来完整、算起来不通」的长文
```

因为 `audit_rendered_article.py` 测的是**长度与结构**，不测**数字是否算得通、
角色是否存在**。而头条号的目标读者（中老年男性）最爱「算账」题材 ——
月费、退休金、份子钱、存款、遗产分配。这类题材的每一篇都在做算术，
算错就等于自曝。

**读者只要拿计算器一按就穿帮**，而且这种穿帮比「文章不好看」更伤：
它让读者怀疑整篇文章都是编的。

## 实测：本轮 6 处硬伤（全部在已投递产物中）

审计对象：`20261101_2030_养老院.html`（《78岁老人住进养老院，一个月8000，
儿女算完这笔账，谁都不说话了》）

### 1. 数值链断裂（SUM_EXCEEDS_FEE）

```
养老院……月费8000。……老大出了5000，老二出了5000，老三出了3000，
剩下的一大半是她自己掏的。
                    ^^^^^^^^ 5000+5000+3000 = 13000 > 8000
```

同一篇里护工小张又说「孩子们加起来才出一半多」—— 13000 是 8000 的
**1.6 倍**，不是一半多。两处互相打脸，读者一算就发现。

### 2. 角色凭空多出（PHANTOM_SON）

老陈明写「**两个女儿**，一个在本市，一个在深圳」，但：

| 位置 | 原文 | 问题 |
|------|------|------|
| `story_b_ending` | 「你不跟**儿子**住，跟女儿住不是正好吗？」 | 只有女儿的人凭空有了儿子 |
| 扩写段落 | 「他**不跟儿子要钱**，房租是他自己的」 | 同上，且与下条矛盾 |
| 扩写段落 | 「两个女儿现在每个月加起来打16次电话」 | 与基础段「每月15号轮流打」矛盾 |

### 3. 同篇自相矛盾（PERIODIC_VS_COUNT）

基础段：「每个月15号，两个女儿轮流打电话来」= **1 通/月**
扩写段：「两个女儿现在每个月加起来打16次电话」= **16 通/月**

### 4. 经费来源矛盾

```
基础段：两个女儿每月各给1000，一个月2000，房租1600，剩下他用退休金补
扩写段：他不跟儿子要钱，房租是他自己的，1600，是退休金的三分之一
```

「女儿给钱」和「不跟女儿要钱」不能同时成立。

### 5. 拆分项之和 ≠ 总额（SPLIT_VS_TOTAL，微头条《立遗嘱》）

```
存款22万……存款按三个孩子平分，一人7万3，剩下的5万1留给他和老伴看病
                      ^^^^^^^ 5.3×3 + 6.1 = 22  ✓ 正确算法
原文写成：7万3×3 + 5万1 = 27 ≠ 22              ✗
```

### 6. 分摊额 ≠ 实际费用（CONTRIB_VS_FEE）

```
一天50块，一个月1500，一年18000。三个儿子商量，每家每月出600，
加起来1800，刚好够钟点工的钱。
                      ^^^^^^ 1800 ≠ 1500，「刚好够」不成立
```

## 根因：内容是「多处拼接」出来的

关键在于这类内容**不是一个字符串**，而是多个来源在渲染时拼起来的：

```
选题池条目（toutiao_topics_extra.py）
    ├─ story_a           ← 基础故事A
    ├─ story_a_dialogue  ← 对话（另一处写的）
    ├─ story_a_ending    ← 结局
    ├─ story_b           ← 基础故事B
    └─ story_b_ending    ← 结局
扩写段落（toutiao_story_extensions.py）  ← ★ 独立文件，渲染时才拼接
    ├─ (extra_a) → 拼到 story_a 末尾
    └─ (extra_b) → 拼到 story_b 末尾
```

**扩写段落是独立文件**，作者视角是「给这个方向补一段」，看不到基础段落里
已经写了什么。于是：

- 基础段写「两个女儿每月各给1000」
- 扩写段落写「他不跟儿子要钱」

两边都没错，**合起来错**。只查单个文件永远查不出来。

## 检查策略：两层 + 单元切分

### 层级一：字段级（数值链）

在**单个字段内**验证算式：

| 检查码 | 含义 |
|--------|------|
| `SUM_EXCEEDS_FEE` | 逐项出资合计 > 同段声明的月费/费用 |
| `SUM_VS_HALF_CLAIM` | 合计与「才出一半多」类断言冲突 |
| `SPLIT_VS_TOTAL` | 拆分项之和 ≠ 总额（「一人X×N + 剩下的Y ≠ 总额Z」） |
| `FRACTION_MISMATCH` | 「A 是 B 的三分之一」推算出的 B ≠ 文中 B |
| `PERIOD_MONTH_YEAR` | 「一个月X」与「一年Y」不满足 Y ≈ 12X |
| `PERIOD_DAY_MONTH` | 「一天N块」与「一个月M」不满足 M ≈ 30N |
| `CONTRIB_VS_FEE` | 「每家每月出X，加起来Y」≠ 同段月费 Z |
| `CONTRIB_SUM_MISMATCH` | 「每份X」× N ≠ 「加起来Y」 |

### 层级二：单元级（角色 / 频次）

在**跨字段的故事单元**内验证一致性：

| 检查码 | 含义 |
|--------|------|
| `PHANTOM_SON` | 单元声明「两个女儿」且无「有个儿子」式声明，却出现「儿子」 |
| `FREQ_CONFLICT` | 同一故事出现多个不同频次声明（来了4次 / 来了12次） |
| `PERIODIC_VS_COUNT` | 「轮流/每人」（一周期一次）vs 「N次电话」 |

### ⚠️ 关键：故事A 与故事B 必须切成两个单元

**这是最容易写错的地方。** 故事A 和故事B 是**不同人物**：

- 养老院故事A 的刘婶：三个孩子 = 老大/老二/老三（**两个儿子一个女儿**）
- 养老院故事B 的老陈：**两个女儿**

如果把 A、B 合并成一个单元查角色，故事A 里那句合法的「刘婶躺在床上
第三个月，**跟儿子说**：'我住养老院吧'」会被误报成 PHANTOM_SON。

正确切法：

```python
unit_a = story_a + story_a_dialogue + story_a_ending + ext_a
unit_b = story_b + story_b_ending                 + ext_b
unit_m = content + micro_dialogue          # 微头条是独立单元
```

扩写段落必须并进**对应**的单元（`extra_a` → unit_a，`extra_b` → unit_b），
不能一股脑拼到后面。

## 中文金额口语缩写（解析陷阱）

自洽性检查的解析器**必须**还原这些省略写法，否则算式全部误判：

| 写法 | 实际值 | 说明 |
|------|--------|------|
| `7万3` | 73000 | 万位 + 尾数省略单位 |
| `一万五` | 15000 | 省略「千」 |
| `五千八` | 5800 | 省略「百」 |
| `8万7` | 87000 | 同「7万3」 |

初版解析器漏了「7万3」，把 73000 当成 7.3，导致 SPLIT_VS_TOTAL 报出
`一人 7.0 × 3 + 剩下 5.0 = 26 ≠ 22` 这种看似合理、实则单位错乱的结论。
**写完检查器要用已知正确的算例验证解析器**，不能只看它「有没有报错」。

## 通用化：linter 脚本

`scripts/lint_content_consistency.py` 是通用实现：

```bash
# 头条号（默认）
python3 ~/.hermes/skills/productivity/content-platforms/scripts/lint_content_consistency.py

# 其他内容脚本
python3 .../lint_content_consistency.py --pool ~/.hermes/cron/scripts/<script>.py

# 指定扩写模块
python3 .../lint_content_consistency.py --pool <script>.py --extensions <ext>.py

# 机器可读
python3 .../lint_content_consistency.py --json
```

自动发现：选题池属性名（`TOPICS_POOL` / `MICRO_TOPICS_POOL` / `TOPICS` …）
与扩写属性名（`STORY_EXTENSIONS` / `TOPIC_EXTENSIONS` …）；
扩写模块默认在 pool 同目录按 `<stem>_story_extensions` 查找。

**头条号本地副本**：`~/.hermes/cron/scripts/toutiao_content_lint.py`
（硬编码头条号路径，改生成器后直接跑它）。

## 修复工作流

1. 备份三个源文件：
   `toutiao-article-daily.py` / `toutiao_topics_extra.py` / `toutiao_story_extensions.py`
2. 跑 linter 拿到清单
3. 逐条改**源文**（不是改产物 —— 产物已投递，改了也没用）
4. 改完跑 linter 直到退出码 0
5. **不要重跑生成脚本**（Case R）：会生成不同随机选题、产生第二份产物、
   且污染 topic_history。改源码对明晚生效即可。

## 与 Case R 的关系

`cron-job-debugging` 的 Case R 规定「已有今日产物就不要重跑脚本」。
自洽性缺陷的修复**不违反** Case R：

- 改的是**源码**，今晚已投递的产物不动
- 用 **linter 验证**，不是靠「重跑一遍看看」
- 明晚起自动生效

这正是 `cron-job-debugging` 里「Case R 与『修内容』有张力 —— 用修代码而不是
重跑来化解」那条规则的又一个实例：**修源码 + 隔离验证，不重跑生产脚本。**

## 给其他内容平台的推广

公众号 / 小红书 / 抖音线只要写「具体数字 + 算账」类内容（这几乎是
情感/家庭类的标配），同样适用：

- 情感文里的「退休金3500，开销3500，每年亏6000，30万能花50年」→ 算式链
- 小红书里的「人均预算 / 花费合计 / 每日均价」→ 算式链
- 任何「他/她有三个孩子，其中两个儿子一个女儿」→ PHANTOM_SON

先在一个平台跑通，再推广。
