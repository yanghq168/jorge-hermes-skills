# 守卫窗口 vs 选题轮换周期 —— 跨夜碰撞的第二个根因（2026-11-14 实测）

**这是 session-detail 参考文件。** 类级方法论在 `../SKILL.md`；缺陷十三（跨夜碰撞）
的检测代码与调参表在 `references/cross-field-defect-detection.md`。

本文件补充**缺陷十三的第二个、也是更隐蔽的根因**：守卫窗口长度与选题池轮换周期的
关系。2026-11-14 当晚按缺陷十三的修法（`SHADOW_GUARD_NIGHTS = 3`）跑完，
audit/lint 全绿，飞书已送达 —— **仍然撞了**。

---

## 现象

2026-11-14 当晚微头条①（老周头、随20年份子钱、老伴去世后烧本子）
与 **11-10 长文《随礼人情》** 是同一个故事；该故事还在 **11-11 微头条**出现过。
⇒ 五天内读者会连续读到三遍同一个故事。

## 根因：守卫窗口 < 轮换周期

| 量 | 数值 | 来源 |
|---|---|---|
| 微头条池大小 | 10 条 | `MICRO_TOPICS_POOL` |
| 每晚发微头条 | 2 条 | `generate_micro_articles()` |
| **微头条轮换周期** | **5 天**（10 ÷ 2） | 计算 |
| `SHADOW_GUARD_NIGHTS` | 3 | 缺陷十三的调参结论 |
| 长文池大小 | 10 条 | `TOPICS_POOL` |
| **长文轮换周期** | **10 天** | 计算 |

**守卫窗口（3 夜）比微头条轮换周期（5 夜）短 ⇒ 被守卫放掉的孪生故事
会在第 4、5 夜重新漏进来。**

缺陷十三的调参表是在「60 天内长文方向按 LRU 轮换」的前提下测的，
只统计了「碰撞当夜」和「碰撞前 1–3 夜」，**没有统计「第 4 夜及以后」的碰撞**。
换句话说：**调参表的观测窗口本身比轮换周期短**，所以「0/60」是假绿。

## 检测口径（与缺陷十三的关键差异）

缺陷十三的检测脚本用 `for back in range(1, 4)` —— **只回看 3 夜**。
正确的做法是**回看整个轮换周期**：

```python
# ❌ 只看 3 夜 → 漏掉第 4、5 夜的碰撞
for back in range(1, 4): ...

# ✅ 回看 max(轮换周期, 守卫窗口) 夜
LOOKBACK = max(
    len(tg.MICRO_TOPICS_POOL) // 2,      # 微头条轮换周期 = 5
    tg.SHADOW_GUARD_NIGHTS,              # 守卫窗口 = 3
)
for back in range(1, LOOKBACK + 1): ...
```

**规则：碰撞回看窗口必须 ≥ 被测池的轮换周期**，否则统计一定偏乐观。
同理，`_predict_next_long_directions()` 的前推窗口也要按长文轮换周期（10 夜）算，
不能只前推 3 夜。

## 调参的代价（这次必须一起算）

把 `SHADOW_GUARD_NIGHTS` 加到 5（= 微头条轮换周期）确实能归零碰撞，
但缺陷十三的调参表已经指出：**5/5 会把微头条方向覆盖压到 4/10**。
守卫夜数一大，10 条微头条里有 6 条是影子方向，被挤掉。

⇒ **两条路，必须选一条，不能两条都走**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 加长守卫 | `SHADOW_GUARD_NIGHTS = 5` | 微头条方向覆盖 10/10 → **4/10** ❌ |
| B. 换掉孪生故事 | **改写**被撞故事的内容（见下） | 需要人工改文案，工作量大但零覆盖损失 |

> ⚠️ **2026-11-15 更正**：上表说「必须选一条，不能两条都走」是**错的** ——
> 真正的结论是 **A 和 B 必须配套做**，只是**顺序有讲究**：
> **先做 B（换掉孪生），A（加长守卫）才不会有覆盖损失**。
> 池里没有孪生故事时，守卫排除集是空的，加长守卫不压覆盖；
> 反过来（先 A 后 B）会白挨一次 4/10 的覆盖损失。
> 11-15 最终形态 = **B 换掉 6 条孪生 + A 守卫动态推导** ⇒ 碰撞 0/60 且覆盖 10/10。
> 详见文末「✅ 2026-11-15：修复已落地」章节。

**本会话实际走的是 B 的半成品**：起草了 6 条与长文不重复的新微头条，
但初稿正文为 **285–324 个中文字**，**全部超过 250 字上限** ⇒ 没有写进生产源码。

## ⚠️ 关键纪律：微头条是 150–250 字的**硬约束**

新写的微头条容易超长，因为「要讲一个完整故事 + 要跟长文不重复」会自然膨胀。
**改完必须立刻量 CJK 字数**，不要等渲染后才看：

```python
import re
def cjk(s): return len(re.findall(r'[一-鿿]', s or ''))
for k, t in MICRO_TOPICS_POOL.items():
    n = cjk(t['content'])
    if not (150 <= n <= 250):
        print(f'!! {k}  content CJK={n}')   # 本次实测：285/272/324/307/289/308 全部越界
```

**没有压进 250 字以内之前，不要把新条目写进生产池。**
理由：`lint_content_consistency.py` **不查字数区间**（它查数值链），
字数越界只有 `audit_rendered_article.py --pool` 的 `--pool` 输出会报 —— 那是渲染后才看得到的。
带着越界条目进池 = 明晚首跑就产出一批超长微头条，而那时人已经睡了、邮件已经发了。

**压缩技巧**：把微头条的 `content` 写成「一个场景 + 一句刺痛的话 + 一个反问」，
而不是完整叙事；具体的人名/金额/后果留给长文池。微头条本来就是短打，
追求「短而扎」不是「短而全」。

## 正确的修法顺序（写给未来的自己）

1. **先扩池再改守卫**。根治办法是扩 `MICRO_TOPICS_POOL`（10 → 12+），
   让轮换周期变长，同时新增条目本身就不与长文孪生。
2. **新条目必须先过 CJK 字数检查**（150–250），再进池。
3. **新条目必须与长文池的所有故事做人工比对**（同人物/同事件/同金句/同金额）。
4. **碰撞检测脚本的回看窗口改成 `max(轮换周期, 守卫窗口)`**，否则统计还是假绿。
5. 改完用**隔离 harness**（`references/isolated-verification-harness.md`）验证：
   碰撞 0 + 两池方向覆盖 10/10 + **生产 history mtime 不变**。
6. **不要用 harness 产物补发** —— 那等于投递第二份内容。
7. 交付报告里写明「读者手上的那份仍是修复前版本，修复从明晚首跑生效」。

## 🛠️ 落地时的代码编辑陷阱（本次实际踩到，2026-11-15）

这三条**都不是内容问题**，而是「用脚本批量改 Python 源码」这一动作本身会踩的坑。
它们的共同症状是：**`py_compile` 通过、但运行时行为没变** —— 或者直接语法错。

### 陷阱 1：`str.replace(old, new, 1)` 可能命中 docstring 而不是代码

**实测**：把 `SHADOW_GUARD_NIGHTS = 3` 改成动态推导函数时，用了
`src.replace("SHADOW_GUARD_NIGHTS = 3", new_block, 1)`。
**文件头 docstring 里也有一模一样的字符串**（历史升级说明里写了
「（`SHADOW_GUARD_NIGHTS = 3`）」），`count=1` 的替换**命中了 docstring**，
真正的代码处（第 1207 行）**一个字都没改**。

**症状**：`py_compile` 通过 ✅、脚本能跑 ✅，但 `SHADOW_GUARD_NIGHTS` 运行时
**仍然是 3** —— 改动完全没生效。

**修法**：
- 锚点**必须带上下文**（前后各一行），不要用「一个孤立的赋值语句」当锚点：
  ```python
  old = "SHADOW_GUARD_NIGHTS = 3\n\n\ndef _recent_long_directions("
  new = "...动态推导...\n\n\ndef _recent_long_directions("
  ```
- **改完必须回读断言运行值**，不能只看「replace 成功」：
  ```python
  assert "SHADOW_GUARD_NIGHTS = _shadow_guard_nights()" in src
  # 还要确认旧串在代码区已消失（docstring 里允许残留）
  ```
- 最保险：**改完 import 一次，打印运行时值**（`print(m.SHADOW_GUARD_NIGHTS)`），
  确认它等于你期望的推导结果（本次 6，而不是 3）。

### 陷阱 2：按花括号深度切分 list 字面量，join 时会留下孤立逗号

**实测**：要删掉 `MICRO_TOPICS_POOL` 里的两条孪生条目，用「按 `{`/`}` 深度
切分出每条 entry」的办法拿到干净的条目片段，然后 `'\n'.join('    '+e for e in keep)`。
问题在于：切出来的 entry 片段**尾部带着原本的逗号**，而**第一条 entry 的
前导逗号**（`[` 后面那个）残留在了旧 block 里 —— 拼回去后变成：

```python
MICRO_TOPICS_POOL = [
    ,          # ← 孤立逗号 → SyntaxError: invalid syntax
    {
        "direction": "婆媳关系",
```

**症状**：`py_compile` 报 `line 133, SyntaxError: invalid syntax`。

**修法**：切分后**重新拼装整个 list 字面量**，而不是拼接切分片段：
```python
new_block = 'MICRO_TOPICS_POOL = [\n' + '\n'.join('    ' + e for e in keep) + '\n]\n'
# 且要确认每个 e 自身不带尾逗号（或统一 strip 后再加）
```
**通用规则**：批量改 list/dict 字面量时，**用「重新生成整个字面量」而不是
「切出片段再拼接」** —— 前者幂等、不留残留分隔符；后者必然要处理
首尾逗号这种边界。

### 陷阱 3：锚点没匹配上时，要先 `find()` 打印真实源文本

本次两次锚点失败都是**照抄记忆里的锚点**（源码里是 `\'` 转义形式、
或少了/多了一个字）。**修法**（沿用本技能既有纪律，这里再强调一次，
因为它在「改生产池」这种动作上代价很高）：
```python
if old not in src:
    i = src.find(anchor_prefix)      # 先打印真实上下文
    print(src[i-80:i+160])
    raise SystemExit("锚点未匹配")
```

## 🔬 反向验证：证明「改动带来了行为变化」而不只是「现在看起来对」

**只跑修复后的 harness 不够** —— 「碰撞 0/60」也可能是**本来就没有碰撞**，
或者你的检测口径写错了导致永远为 0。

**本次做法（可复用）**：在同一个 harness 里**分别跑「修复前」和「修复后」两套配置**，
用同一份种子 history、同一段模拟代码、同一份碰撞检测口径，只有池/映射/守卫参数不同：

```python
def simulate(micro_pool, shadow_map, guard, nights=60):
    m.MICRO_TOPICS_POOL = micro_pool
    m.SHADOW_MAP = shadow_map
    m.SHADOW_GUARD_NIGHTS = guard
    # 每轮都从同一份生产 history 复制种子（shutil.copy），保证起点一致
    ...
    return nights_list   # 每夜 (长文方向, [微头条方向...])

# 修复前：用备份脚本里的旧池 + 旧 SHADOW_MAP + 旧守卫
# 修复后：新池 + 空 SHADOW_MAP + 新守卫
```

实测结果：

| | 跨夜孪生碰撞 | 微头条方向覆盖 |
|---|---|---|
| 修复前（旧池 + 旧映射 + 守卫 3） | **12/60 夜**（全部命中在距离 **4 夜**） | 10/10 |
| 修复后（新池 + 空映射 + 守卫 6） | **0/60 夜** | **10/10** |

**「修复前 12/60、修复后 0/60」这一对照，才是改动生效的证据**；
只报「修复后 0/60」无法区分「改好了」与「检测器坏了」。

⚠️ **「修复前」那套配置从哪来**：本部署 `/tmp/bak_toutiao-article-daily.py` 有
11-06 的旧脚本备份 ⇒ `importlib` 加载它就能拿到**真实的旧池**（带完整
`tags`/`content`/`hook` 字段）。⚠️ **不要手搓 stub 条目** —— 只填 `direction`
和 `title` 的 stub 会在 `generate_micro_articles()` 渲染时
`KeyError: 'tags'` 炸掉（本次就踩了一次）。
**要么从备份脚本 import 真实旧池，要么把 stub 的字段补全。**

⚠️ **修复前的模拟会污染 history** —— 每次 `simulate()` 开头必须
`shutil.copy(生产history, 临时history)` 重置种子，否则第二轮跑的是第一轮的
后状态，两组数据不可比。
